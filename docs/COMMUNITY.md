# Players, follows, and community stories

Open **Community** in the main navigation. The first community feed contains public reviews from authors who have opted into a public player profile. **Everyone** shows all eligible reviews; **Following** requires login and limits the same query to followed authors. Reviews sort by most recently edited, then ID, with 8 per page. This is a view of current published reviews, not an immutable event history. Deleted reviews, unpublished reviews, and hidden profiles leave the feed immediately on the next request.

The feed uses a centered 896px content container, with a narrower centered 672px review column. Friend shelves, section headings, feed tabs, empty states, and controls share a restrained sans-serif type scale. Review cards use 36px covers on phones and 44px on larger screens, 14px titles, 12px body text, and 11px metadata. Long or multiline reviews initially show three lines with **Read more** and **Show less** controls; full text remains available. Spoiler reviews stay behind an explicit disclosure. Small actions and review pagination use 28px controls. Pagination shares the review column width, preserves the selected feed, and returns to the top when changing pages.

## Friend game shelves

Signed-in visitors see **New from friends** and **Popular with friends** above the reviews on the first review page, in both Everyone and Following views. Friends means players the viewer follows; reciprocal follows are not required. Guest pages and later review pages retain the review feed without loading these personalized shelves. Responses use `Cache-Control: private, no-store`.

Only current Playing, Paused, and Completed entries from followed players with an active public profile and username qualify. The viewer's own library, non-followed users, private profiles, Dropped entries, and entries without status are excluded. Hiding a profile, unfollowing, deleting an entry, or leaving an eligible status removes it on the next read. The profile visibility helper explains status sharing to followers.

New from friends shows the current most recent status per player/game, rather than an immutable event log. `library_entries.status_changed_at` changes only when the status changes, including initial assignment; rating, review, favorite, and diary edits do not refresh it. The new nullable column has no historical backfill. A known legacy Completed timestamp is used as a fallback; other unknown dates sort last and say **Date not recorded**. Client requests cannot set this timestamp.

Popular with friends ranks games by distinct eligible followed players, then their latest known status time and game ID. It measures current shared playing states, not weekly activity, ratings, or favorites. Both shelves initially show six compact covers; native expandable rows show up to twelve results. Cards include validated game artwork and titles; activity cards add a public alias/avatar, status, and date, while popular cards show a friend count. Payloads omit library IDs, favorites, individual ratings, reviews, diary text, and login identity.

## Player profiles

The profile layout places the circular avatar, name, actions, and bio on the left, with summary values on the right. There is no additional profile tab bar. Public profiles keep Top 4, recent completions, and recent public reviews in the main column, with public lists in the sidebar. Review rows show a thumbnail, title, release year, rating, date, and spoiler-aware body.

**Profile** at `/community/profile` is now an owner-only, read-only overview, available even before a public profile is configured. It shows saved Top 4 picks, four recently active games, and the owner's latest reviews, including clearly marked private reviews. It does not create a profile or publish any data on read. The account menu links here. Only the header's **Edit profile** action opens the dedicated editor at `/community/profile/edit`; photo controls sit above the two columns, with information on the left and Top 4 controls on the right. Existing named update/photo/showcase routes redirect back to this editor. No editing controls appear beneath Top 4 on either overview.

Activity is limited to four distinct games in the authenticated user's library, ordered by the latest retained update timestamp across library entries, ratings, reviews, playthroughs, and diary entries, with entry ID breaking ties. It is a current summary, not an immutable activity log. Diary notes and playthrough details are not returned. Owner review pagination uses four rows and `reviews_page`; private reviews and this broader activity are never added to `/players/{username}` or community feeds. Public profiles automatically include their latest four completed games; Private hides the public profile.

The editor places photo controls at the top, information on the left, and Top 4 on the right. Photo, information, and shelf forms save independently: new players can upload a photo or save favorites immediately, creating a private profile without choosing a username. Only valid mutations create that profile; editor and overview reads stay read-only. Username, display name, bio, location, and publication remain in the information form. Accounts are not automatically listed in discovery.

Players can upload, replace, preview, and remove a profile photo. Photos follow profile visibility and appear consistently across the public profile, discovery, public contributions, and account avatar. See [photo storage, formats, and cleanup](PROFILE_PHOTOS.md).

- Usernames contain 3–30 ASCII characters, start with a letter, and permit letters, digits, and underscores. Input is normalized to lowercase; the database also enforces case-insensitive uniqueness. A username change changes the public profile link.
- Display names are required, up to 80 characters. Bios are optional, up to 1,000 characters, rendered as plain text.
- Location is optional plain text up to 120 characters (for example, a city and country). It is shown on the owner's overview and shared on public profiles only when the profile is public. Empty input clears it; omitted location values preserve the existing location. No geolocation service or device location permission is used. The nullable column is introduced by `2026_10_30_040000_add_location_to_user_profiles`.
- `/players` searches public usernames and display names, with literal SQL wildcard handling and 18 results per page. Email and account names are not search fields. Signed-in discovery excludes the viewer's own account; their profile remains accessible from the account menu and profile editor. Guests can discover the first opted-in public player.
- `/players/{username}` accepts case-insensitive username lookups. It exposes the chosen public identity, follow counts, manually selected Top 4 games, public reviews, public lists, and optionally the latest four completed games. Review and list pagination use separate `reviews_page` and `lists_page` parameters.
- Private profiles return 404, including to the owner; owners manage them through the authenticated editor.
- Public data uses explicit resource fields. The profile never exposes login credentials, email, unshared library records, library favorite flags, playthroughs, diary entries, private reviews, or private/unlisted lists. Public reviews and lists use the public alias while the profile is active. Recent completions follow profile visibility; see [profile shelves](PROFILE_SHELVES.md).
- Switching off the profile hides it from player discovery and community feeds. Existing publicly shared reviews remain on game pages, and public lists remain accessible through their existing list routes and discovery. Their own visibility controls still apply. The chosen display name remains on those public contributions, while the profile link disappears. Follow relationships are retained if a player hides their profile.

## Player discovery layout

The Players page uses a centered 896px container, a short centered introduction, and a compact search toolbar. Portraits use five columns on desktop, three on tablet, and two on phones, with 88–120px circular avatars. Each real public player card shows a 14px display name, 11px username and follower/public-review counts, and the manually selected Top 4 games in saved order. Page controls and circular follow actions are 28px; typography uses PlayHaven's global sans-serif font. Empty states stay compact and distinguish an empty directory, no search matches, and an out-of-range page. Missing favorites use a short text fallback. Counts never include private reviews or private library totals; cover links use the existing validated game artwork resource.

The circular follow action uses the existing follow endpoints and stays on Players after follow/unfollow. A validated directory flag retains the search query, page, and scroll; the refreshed page updates follow buttons and follower counts. Avatar and name links still open the profile. Follow actions made on a profile retain their existing profile redirect. Guest actions lead to login. Search, pagination, and profile visibility rules still apply. Card data is eager loaded for the directory page, and no external catalog API is called.

When no other public profiles exist, signed-in players see **No other players yet.** with a profile setup link. Guests with no public profiles see **No players here yet.** A search miss in an existing directory uses **No players found.**, and an out-of-range page links back to the first page. These states are based on available public profiles rather than a hardcoded account count. No sample accounts or profiles are inserted into the development database.

## Following

Follow or unfollow from another public player's profile. Login is required; publishing one's own profile is optional. The server derives the follower from the authenticated session, rejects following oneself, validates that the target is public, and treats repeated follow/unfollow operations idempotently. Follow mutations share a limit of 30 per minute per user. Existing email verification rules apply, including the configured local-development bypass.

No email, push notification, recurring import, or external API request is triggered by following. Community reviews require publication. Personalized friend shelves separately expose the eligible current statuses described above; the full library, private reviews, and diary remain private. Spoiler reviews remain collapsed until expanded.

## Storage and verification

The feature reuses `user_profiles` and `follows`. An additive migration introduces `user_profiles.is_public` with a false default and an index on `reviews (is_public, updated_at, id)`. It does not alter player history or publish existing accounts. Eager loading supplies author profiles, ratings, and local game metadata; nested game resources are resolved before Inertia traverses them.

`CommunityTest` covers opt-in publishing, ownership, username normalization/collisions, follow direction/idempotency/self-follow prevention, authentication, throttling, feed filtering, privacy changes, spoiler metadata, pagination, safe resources, and game-review author links on SQLite and isolated PostgreSQL. Browser checks use temporary local accounts, exercise actual login and profile/follow forms, and remove their records afterward.
